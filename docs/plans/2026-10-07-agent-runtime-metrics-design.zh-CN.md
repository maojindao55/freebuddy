# FreeBuddy 第三列运行指标卡片方案（第一期）

日期：2026-10-07。状态：第一期已实施，完成类型检查、构建及自动化验证。

最新范围：**第一期只做第三列现有「运行状态」card 的指标展示，以及支撑该展示的最小采集和本轮数据关联。**

## 1. 首期交付范围

在现有 `WorkspacePanel` 的运行状态卡片内增加「本轮运行」指标区，让用户在对话旁看到首字延迟、生成速度、输入/输出 Token 和总耗时。

数据对应当前会话的当前执行；执行结束后显示最近一次结果。新一轮立即重置。复用既有流事件、usage 数据和任务/消息存储，不先建设通用运行日志系统。

| 首期包含 | 后续范围 |
| --- | --- |
| 第三列卡片的四项指标、状态和缺失提示 | 历史运行日志页、筛选、搜索和分页 |
| 当前执行与指标的绑定，结束后固定结果 | 独立运行详情页、时间线和重试详情 |
| 必要的 Host 首字与耗时观测，已有上报指标归并 | 性能概览、P50/P95、跨 Agent/模型对比 |
| 中英文文案、来源提示与关键行为验证 | CSV/JSONL 导出、保留策略与历史回填 |
| 通过既有任务/消息链路保存最小结果摘要 | 独立运行/attempt 数据表、通用日志查询 API、逐模型调用分析 |

卡片不提供指向尚未实现的「查看运行记录」或详情页的按钮。累计用量页面继续使用已有数据源。

## 3. 卡片内容与交互

在既有卡片中以「本轮运行」标识当前执行，结束后改为「最近一次运行」。保留紧凑的两列指标布局，沿用现有卡片样式与主题。

| 项目 | 有数据时 | 运行中尚无数据 | 结束后缺失 |
| --- | --- | --- | --- |
| 首字延迟 | 如 `1.28 s` | `等待首字`，准备阶段可显示 `准备中` | `未产生正文` 或 `不可测` |
| 生成速度 | 如 `52.4 tok/s`，标明实测 / 流式观测 / 上报 | 新执行显示 `测速中` | 缺少有效测量或真实 Token 显示 `不可测` |
| 输入 / 输出 Token | 如 `3.2K / 860` | 已知项显示数值，未知项显示 `—` | `—` 并提示具体原因 |
| 总耗时 | 如 `28.6 s` | 低频递增 | 固定实际结束时的时长 |

以上数值仅为显示示例。

- 状态来自当前会话所绑定的执行；全局 `runningCount` 不能代替本会话状态。
- 新一轮开始立即绑定新的执行标识，清空上一轮的首字、速度、Token 和计时结果。
- 当前会话从未执行过时显示「尚无运行」，不展示假数据或 0 tok/s。
- 完成、失败、取消、超时和委派 yield 分别呈现，不能仅根据 exitCode 0 判定完整任务成功。
- 指标名称或信息图标的提示说明来源与口径；真实 0 与缺失值分开。
- 输入/输出 Token 不再因同时有 context/cost 数据而被隐藏；上下文占用属于另一项数据。
- 已有缓存、思考 Token、LLM 耗时等辅助字段可继续显示或收纳，首期不增加独立分析流程。
- 切换会话读取各自的运行摘要；卡片收起或重新展开不重启计时。

团队会话显示整体状态和可验证的整体耗时。不能把某个成员的速度当成团队速度，也不能相加成员 tok/s；成员指标仅在能够明确绑定成员与执行时展示，不为首期扩建团队分析面板。

## 4. 指标口径

### 首字延迟与 TTFT

默认展示 Host 观测的本轮首字延迟：

`first_text_latency_ms = 首段新 assistant 正文到达时间 - 本轮最初 prompt 提交时间`

ACP 在实际 `session/prompt` 写入处建立提交时间。原始片段进入 Host 时捕获单调时间，通过回放/内容判断后确认首字，并在现有 80ms 界面合批之前完成观测。

排除历史回放、用户回显、初始化消息、思考片段、工具活动和空片段。重试前一直没有正文时，不在重试后重置最初提交时间；卡片反映本轮实际等待。

上游 `avgTtftMs` 另存来源；若只能展示该值，标签明确为「平均 TTFT · 上报」，不能悄悄替代观测首字延迟。整段响应、raw 输出无法识别正文、历史回放无法可靠区分等情况显示具体限制。

TTFT 的客户端测量通常采用请求发送到首个流式输出的间隔，比较时必须明确边界；Host 首字观测与模型服务内部指标分别保存。[vLLM 指标说明](https://github.com/vllm-project/vllm/blob/main/docs/benchmarking/cli.md)

### 生成速度 tok/s

用户追加要求自动测速后，Pi 使用 FreeBuddy 管理的原生扩展，在每次实际 assistant 流式输出的首个非空正文、思考或工具参数 delta 到 message_end 之间使用单调时钟计时，扣除扩展 UI 阻塞等待。工具执行、调用之间等待和首包等待不进入计时。

本轮速度为 `各次调用的真实输出 Token 之和 / 各次有效生成秒数之和`，不能直接平均各次 tok/s。输出 Token 沿用模型真实 usage，包含思考与工具参数；不以字符数或 chunk 数估算 Token，也不把 `输出 Token / 运行总耗时` 标成生成速度。该口径包含客户端流传输开销，不等同于服务端纯 decode 速度。

扩展只在原生会话中写数字 custom entry，不进入 LLM 上下文。Host 使用 prompt 前的原生日志位置读取本轮新增记录，仅在每次调用的计时与输出用量完整匹配时计算。整段返回、单个有效 delta、低于 1ms 的区间、缺失 Token 或调用覆盖不完整均保持不可测，避免虚假的速度。每轮结束后在现有卡片显示结果和「实测」来源，无须 Agent 在正文中回答速度。

用户进一步要求统一测量其他 CLI，并明确选择「缺少真实 Token 时保留不可测，只显示真实 tok/s」。Host 增加通用流式观测层，所有 ACP 适配器及可识别的 legacy JSON 流复用同一个采集器：在回放过滤之后记录正文/思考 delta，在工具调用、权限等待、完整响应或 prompt 完成时切分区间。最终真实 turn 输出 Token 除以有效区间总时长，标为「流式观测」，不要求 CLI 提供速度字段。

通用层需要真实本轮计数、至少两个分时到达的有效输出片段及可确认的工具边界。整段返回、仅有 session 累计/上下文用量、无法识别首次输出的工具调用、工具和模型输出重叠、旧协议未知输出和 legacy 不可区分的回放保持不可测。通用协议边界、缓冲和隐藏输出会影响精度，卡片提示明确其精度低于 Pi 原生逐调用计时；每次内部重试清空该次观测区间，初始化与收尾不参与测速。

若本轮 usage 明确包含非零思考 Token，但协议未流式输出思考片段，则正文开始后的区间不能覆盖这些 Token，通用测速保持不可测。思考计数晚到时撤销已计算的流式速度，真实输入/输出用量和首字延迟继续保留；原生提供完整计时的实测不受此限制。AGY 实测日志中，本轮输入 13,276、输出 217、思考 172，而桥接只输出正文；旧计算将 217 除以正文首字到 prompt 返回的约 1.13 秒，得到 192.1 tok/s，现已拒绝这种计时覆盖不完整的结果。

Claude Legacy 默认开启 `--include-partial-messages`，解析正文/思考片段并通过原生 message/block 标识合并最终快照，避免重复显示；Host 单独观测工具参数 delta，不把参数当正文或使用字符数推测 Token。

用户选择 AGY 显示「调用平均速度（含思考、首包等待）」：桥接按本轮完成的 `agent_response` 步骤收集原生 `duration_seconds`，按步骤 ID 去重并求和，通过 `_meta.metrics.modelCallDurationMs` 和明确的 turn scope 返回。排除原生 result 中整个会话累计的耗时，以及独立工具步骤、CLI 初始化和调用之间的等待。每次调用的用量与耗时必须完整有效；缺少耗时不影响真实 Token 上报。Host 按 `本轮真实输出 Token / 本轮模型调用秒数之和` 计算平均吞吐，卡片来源明确标为「调用平均（含首包）」，并保留首字延迟的原有口径。

优先级为原生流式「实测」→ 明确原生调用耗时的「调用平均（含首包）」→ 通用「流式观测」→ CLI 已有 `tokensPerSecond`「上报」→ 不可测。上报口径未知时保留提示。Pi 桥接未来直接上报 prompt usage 时保留其 Token，但仍单独读取原生计时，二者不互相覆盖。未增加字符/s、Token 估算或历史速度回填。

### 输入 / 输出 Token

只显示可明确归属当前执行的用量，区分增量、本轮累计和原生 session 累计。相同事件不重复计数，最终本轮汇总覆盖同口径临时值。

未知口径或仅有会话累计时，不强行填入本轮数字。现有 tokscale 累计用量不用于分摊本轮 Token，`contextUsed/contextSize` 也不能作为本轮输入用量。缓存与思考 Token 的包含关系沿用已确认的适配器语义。

### 总耗时

从 Host 开始本次执行到实际终态，用 Host 单调时钟计算，包含该入口之后的准备、初始化、工具、等待与重试。卡片低频刷新，结束后冻结。

该值不是浏览器点击到渲染完成的体验延迟。Host 重启后没有完整终态证据时显示中断或缺失，不用重启时间伪造结束时长。

## 5. 最小数据链路

`Host 本轮观测 / 已有 usage → 现有会话流事件 → 对应 run 的摘要 → 第三列 card`

- 每次执行复用当前 session/task 标识；同一个原生 Agent session 连续发送时仍区分本轮。
- Host 维护轻量的本轮计时与摘要，首次正文、可靠用量和实际终态到达时更新；不逐 chunk 写库或推送计时器事件。
- 共享协议中增加可选的本轮指标摘要，保存执行标识、首字延迟、总耗时、状态、来源和缺失原因。可附在既有 usage 流项目中，但必须与上游 metrics 分开命名和归并。
- 通过既有 assistant 消息保存摘要；指标读取仅扫描当前执行/当前 assistant 消息，不能任意搜索到上一轮富 metrics 就返回。
- 首期不新增独立日志表或列表/统计/导出 API。若既有保存链路无法覆盖某路径，只补卡片需要的摘要传递，不扩成通用存储系统。
- 普通会话与工作流/委派的实际执行均从 Host 采集。团队外层没有可验证指标时保留空值。
- 观测/展示故障不阻断 Agent 执行；缺失值保留原因，避免假装测量成功。
- 摘要只包含数值、标识和受控状态，不复制 prompt、回复、思考内容、环境变量或凭证。
- 沿用会话和事件的 owner 隔离，避免完整摘要经通用广播泄露给其他用户。

既有消息中已保存的上报数据可继续读取，但没有本轮观测摘要时不反推首字延迟。首期不承诺跨应用重启恢复运行中的完整性能状态，也不进行历史补算。

## 7. 首期验收

- 本轮首字、生成速度、输入/输出 Token、总耗时能在卡片中按实际数据展示；来源和缺失状态可解释。
- 新一轮开始不会显示上一轮指标；同一原生 session 连续执行仍区分轮次。
- 切换会话与折叠卡片不重启计时、不串数据；全局其他运行不改变当前卡片状态。
- 思考、工具调用、历史回放不会触发正文首字；80ms 展示合批不会增加测量值。
- 失败、取消、超时、重试和 yield 的状态及耗时准确；缺少正文或用量时保留空值。
- 重复/累计 usage 不重复计数；真实 0、未知、待上报和未上报可以区分。
- 团队整体与成员指标不混用，速度不相加。
- 指标采集不会阻断执行，摘要不泄露正文或凭证，事件保持用户范围隔离。

实施时使用现有 `node:test` 与 Electron 测试方式验证关键行为，并执行 `npm run typecheck` 和相关测试。第一期已按上述边界落地；没有新增独立日志页、日志表或查询 API。


## 8. 实施记录

- 在现有运行状态卡片内增加两列四项指标；新执行清空旧值，结束后保留最近摘要。
- Host 使用单调时钟记录执行起止与实际 prompt 提交，在 ACP 回放过滤后、界面合批前确认首段正文。无法可靠区分正文与回放的 legacy 路径保留不可测。
- 生成速度新增 Pi 自动实测及其他 ACP / 可识别 legacy JSON 的 Host 流式观测；本轮 Token 仅采用明确 turn scope 的值，未知口径的 vendor 累计值不进入本轮指标。只返回整段内容或无法提供真实用量的 CLI 保持不可测。
- Pi ACP 旧桥接只转发上下文占用：在 prompt 提交前记录原生 session 日志的字节位置，结束时仅汇总新增 assistant 调用的真实 usage 与数字计时记录。输入包含缓存读写，输出已含思考，不重复累加；优先保留未来桥接直接上报的本轮 usage。取消与 yield 在终态摘要之前收集，缺失或损坏的原生记录保持未知。管理扩展随 Pi 启动幂等安装；新执行不回填历史速度。
- 摘要附着现有 usage 项，经现有 assistant 消息链路保存；同一执行只保留一份最新摘要。
- 完成、失败、取消、超时与 yield 分别呈现；缺少最终摘要的中断记录不伪造总耗时。
- 团队会话仅展示整体状态与可验证耗时；异步加载和切换期间不会借用成员指标。
